# MirrorLife 产品体验闭环

## 1. 目的

本文件是 MirrorLife 后续功能、视觉、性能和上线工作的共同执行标准。它解决的不是“代码有没有写完”，而是：

> 玩家是否能顺畅进入世界，明白要做什么，愿意继续探索，并在整个过程中感到画面可信、操作舒服、反馈有趣、性能稳定。

项目北极星按优先级排序：

1. **游戏流程通畅且好玩**：核心循环清楚，操作有反馈，目标和结果容易理解，玩家有继续玩的动力。
2. **设计过硬且统一**：人物、建筑、室内陈设、动效、界面和叙事属于同一个世界，不出现临时拼装感。
3. **性能在目标设备上稳定**：首次进入、移动、旋转、切换场景和长时间游玩都不能明显卡顿或失控。

如果三者冲突，先保护玩法流程，再寻找不降低设计质感的性能方案。不得用静态截图效果、隐藏假场景、2D 替身或削弱交互来伪造完成度。

## 2. 每项工作的玩家终点

开始设计或开发前，必须先写清楚以下六项。没有答案时，不进入大规模实现：

| 问题 | 必须得到的答案 |
| --- | --- |
| 目标玩家是谁？ | 首次用户、回访用户或深度玩家，以及他们此刻的上下文 |
| 玩家现在想做什么？ | 一个可观察的动作，不是抽象功能名称 |
| 玩家为什么愿意做？ | 好奇、成长、关系、创造、挑战或情绪回报 |
| 玩家如何知道自己做对了？ | 画面、动作、声音、文本、数值或世界状态反馈 |
| 玩家需要等待多久？ | 从输入开始计算的端到端预算，以及等待时看到的反馈 |
| 成功后下一步是什么？ | 下一段玩法是否自然出现，是否形成可重复循环 |

每项任务同时定义：

- **玩家承诺**：完成后玩家实际得到什么。
- **非目标**：本次明确不解决什么，避免范围漂移。
- **体验预算**：时间、帧率、内存、资源体积、draw calls、三角面、操作步骤等上限。
- **保真约束**：不能牺牲的人物身份、3D 环绕、碰撞、交互锚点、场景连续性和美术特征。
- **失败信号**：什么现象出现时说明方案方向错了。

## 3. 六阶段闭环

### 3.1 设计

设计阶段先验证玩家体验，再决定实现方式。

必须产出：

- 一句话玩家旅程：“玩家看到……，尝试……，得到……，因此愿意……”
- 首次 30 秒、首次 5 分钟和一次完整循环的体验流程。
- 核心状态及转移，包括进入、成功、失败、取消、重试、离开和恢复。
- 可点击原型、灰盒或最小垂直切片；重大视觉方向需要正面、侧面、移动中和不同屏幕尺寸证据。
- 美术语言：形状、比例、材质、色彩、光照、动作节奏和禁用风格。
- 性能预算与资源策略，不能等画面完成后再补。

设计门禁：

- 首次玩家不依赖开发者解释也能找到下一步。
- 核心动作有明确即时反馈和后续结果。
- 美术方向能覆盖人物、建筑、室内和界面，不只是单张概念图。
- 技术方案支持真实游玩视角、连续移动和旋转。
- 已列出最可能使玩家流失的三个原因。

### 3.2 开发

开发阶段以垂直切片为单位打通完整玩家路径，避免先堆大量孤立系统。

执行规则：

- 先完成最短可玩闭环，再增加内容密度和精细度。
- 性能埋点、错误观测、降级策略和测试接口与功能一起实现。
- 任何加载优化都按真实输入到可交互结果计时，不能排除同步工作或偷偷预热完整场景。
- 动画必须在运动中审查，人物必须检查轮廓、关节、接触点、脚底种植、遮挡和四向视角。
- 美术资产必须检查裁剪残片、透明边缘、纹理渗色、层级穿插、碰撞和远近景表现。
- 每个结构性改动都要比较改动前后，说明玩家获得了什么、付出了什么。

开发门禁：

- happy path 已能从头玩到尾。
- 中断、快速重复输入、弱设备、缓存失效和场景切换不会破坏状态。
- 没有为了测试或截图存在的产品内假实现。
- 已保存可重复的基线数据，能够发现退化。

### 3.3 验收

验收必须同时回答“能不能用”“好不好玩”“好不好看”“是否稳定”。

验收证据包至少包含：

1. 首次用户完整路径录像或连续截图。
2. 桌面和移动端的真实输入端到端性能数据。
3. 关键场景正面、背面、左右四向和移动中的视觉证据。
4. 核心循环、异常路径、连续切换和长时间运行测试。
5. 人物动作、交互接触、建筑裁剪、室内陈设和界面层级检查。
6. 与任务开始时玩家承诺、预算和非目标逐项对照。
7. 已知风险、影响用户范围、降级方式和后续负责人。

出现以下任一情况不得判定完成：

- 只有构建或单元测试通过，没有真实游玩证据。
- 只有最好看的单一视角，没有移动或环绕检查。
- 平均值达标但首次进入、低端设备或 P95 明显失控。
- 玩家不知道下一步做什么，或等待时没有可理解反馈。
- 新功能破坏既有核心循环、人物身份或统一美术语言。

### 3.4 上线

上线的目标是让改动安全地到达真实玩家，而不是让部署命令成功。

上线前：

- PR、CI、预览环境和必要人工验收全部通过。
- 明确功能开关、回滚提交、数据兼容性和故障降级。
- 记录上线前基线：进入成功率、加载时间、错误率、帧率或长任务、关键行为转化。
- Production 改动必须明确授权；预览通过不等于生产已经验证。

上线后：

- 先检查错误、白屏、资源失败、性能恶化和核心路径中断。
- 再检查玩家是否真正进入、完成和重复核心循环。
- 指标异常时优先保护玩家数据和可玩路径，必要时关闭功能或回滚。

### 3.5 用户视角反馈

反馈不能只收集“喜欢/不喜欢”，要定位玩家在哪一步、为何中断。

使用三类证据：

- **玩家说了什么**：访谈、评论、反馈文本、可用性测试中的原话。
- **玩家做了什么**：首次动作、路径选择、退出点、失败重试、任务完成和回访。
- **设备发生了什么**：加载、错误、内存、长任务、帧率、网络和资源失败。

反馈按体验旅程归类：

1. 看不懂：不知道目标、入口或结果。
2. 不好玩：缺少选择、反馈、变化、挑战或回报。
3. 不好看：风格不统一、动作僵硬、构图混乱或资产有残片。
4. 不顺手：点击、移动、镜头、响应或状态反馈不符合预期。
5. 等不起：加载、卡顿、切换或恢复时间过长。
6. 不可信：碰撞、人物接触、世界状态或叙事结果前后矛盾。

不得用少数强烈评论代替行为数据，也不得用总体平均数据掩盖新玩家或低端设备的问题。

### 3.6 优化

每轮优化只解决有证据的体验问题，并形成新的可验证假设：

> 因为观察到【玩家/设备证据】，如果改变【具体体验或系统】，预计【目标玩家行为或性能指标】会从【基线】变化到【目标】，且不破坏【保真约束】。

优先级按以下顺序判断：

1. 是否阻断核心游戏流程。
2. 影响多少玩家、发生频率和严重程度。
3. 是否损害长期可玩性、视觉信任或产品辨识度。
4. 证据可信度和方案成功概率。
5. 开发、美术、测试和维护成本。

优化完成后必须重新走设计假设、开发验证、验收和上线观察，不能以“已经修过”结束闭环。

## 4. 交叉评审机制

每个重大方案和完成候选至少从以下五个视角独立审查。评审者的任务不是同意，而是主动寻找会让玩家失望的证据。

| 视角 | 核心质疑 |
| --- | --- |
| 玩家 / 产品 | 玩家为什么现在要做这件事？下一步清楚吗？等待和失败是否值得？ |
| 游戏设计 | 是否形成选择、反馈、变化和回报？重复三次后还成立吗？ |
| 游戏美术 | 形状、比例、色彩、材质、光照、动画是否属于同一世界？运动中是否仍成立？ |
| 工程 / 性能 | 成本是否被转移到首次加载、内存、低端设备或后续维护？真实 P95 是多少？ |
| QA / 发布 | 快速点击、取消、恢复、弱网、移动端、长时间运行和旧数据会怎样？ |

必要时增加叙事、无障碍、安全、隐私或运营视角。

每条评审意见采用统一格式：

- **质疑**：可能伤害哪类玩家的哪一步。
- **反例**：在什么设备、路径或状态下出现。
- **证据要求**：用什么截图、录像、指标、测试或原型证伪。
- **结论**：接受、修正、延期或明确承担风险。

评审规则：

- 至少保留一个“反方结论”，即使最终方案通过，也要记录最强反对理由。
- 多个视角一致不等于事实，必须有真实运行证据。
- 出现意见冲突时，以玩家目标和事先定义的预算裁决，而不是以实现成本最低裁决。
- 同一路径连续三次结构性尝试失败时停止试错，回到假设或架构层重新评估。

## 5. 定期目标对齐

以下时点必须进行目标回看：

- 新任务开始时。
- 设计方向或架构发生变化前。
- 每个垂直切片完成后。
- PR 提交前。
- 预览环境验收后、Production 上线前。
- 上线后的首轮数据和用户反馈到达时。
- 连续两次优化没有改善玩家指标时。

目标回看只回答五个问题：

1. 我们现在解决的是哪个玩家问题？
2. 这次改动让核心循环更顺、更有趣或更可信了吗？
3. 玩家能直接感知到改善吗，还是只有内部代码变了？
4. 是否牺牲了视觉、性能、可访问性或其他真实路径？
5. 现有证据足以继续、上线，还是应该停止或换方向？

若答案与原目标不一致，暂停扩展范围，先修正规格、预算和验收方式。

## 6. 分层完成定义

| 层级 | 完成标准 |
| --- | --- |
| 代码完成 | 实现、静态检查和构建通过 |
| 功能完成 | 正常及异常状态正确，自动回归通过 |
| 体验完成 | 首次玩家能独立完成，反馈清楚，核心动作有趣 |
| 视觉完成 | 四向、运动、远近景、桌面和移动端风格统一且无明显瑕疵 |
| 性能完成 | 真实端到端样本和目标分位数达标，内存与降级策略有效 |
| 发布完成 | 预览、CI、回滚和观测齐备，生产状态得到确认 |
| 产品完成 | 上线证据证明玩家问题改善，残余问题进入下一轮优先级 |

默认情况下，MirrorLife 的“完成”至少指体验完成、视觉完成和性能完成。准备上线时必须达到发布完成。上线后只有观察到玩家结果，才进入产品完成。
